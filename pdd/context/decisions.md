## Decision: Fleet Switcher — deck UI state becomes per-voyage + persisted (lossless switch) (Phase 24)
**Date**: 2026-06-22
**What was decided**: Added the **Fleet Switcher**, the GrandLine adaptation of PandaOS "switch context without losing terminal/browser/agent state". The Observation Deck already buffered EVENTS per-voyage (`stores/voyage.ts`: per-voyage `buffers`, an LRU `visitedOrder`, and `selectVoyage(id)` as the switch primitive), but the deck **UI** state — which view you were on, your Ship's Log filters, group-by-phase, scroll — was GLOBAL and bled across voyages on every switch. We made deck UI state **per-voyage and lossless** with a new sibling store `stores/deckState.ts` (Zustand), keyed by `voyageId`: per voyage it holds `lastView: "sea-chart" | "crew-map" | "ships-log"`, `logFilters` (the exact `LogFilters` shape Ship's Log uses), `groupByPhase: boolean`, and `scroll: Partial<Record<view, number>>`. Actions `setLastView`/`setLogFilters`/`setGroupByPhase`/`setScroll` each take a `voyageId`; `getDeckState(voyageId)` returns SANE DEFAULTS (`sea-chart`, `EMPTY_FILTERS`, `groupByPhase:false`, `scroll:{}`) for an unknown voyage WITHOUT mutating the map. The whole keyed map persists to versioned localStorage by REUSING the existing `readPref`/`writePref` helper under a new `DECK_STATE_VERSION` (key `observation_deck.deckState`), hydrating once on store creation and writing on every mutation, so state survives reloads (lossless) and SSR is safe (the helper no-ops without `localStorage`). The **Fleet Switcher** UI (`components/observation-deck/FleetSwitcher.tsx`) is the quick-switch surface: a Command-Palette-consistent overlay listing voyages from `useVoyages` (title + `StatusBadge`, active voyage `aria-current`, recents-first via the voyage store's `visitedOrder`, type-to-filter), and selecting a voyage calls `useVoyageStore.selectVoyage(id)` (the switch primitive — NOT re-implemented) then navigates (`useRouter`) to that voyage's restored `lastView`. Open state is a new `fleetOpen` flag on the existing `ui` store (Esc-closable alongside the palette/help). Triggers: a header "⛵ Fleet" button, a Command-Palette entry "Open Fleet Switcher", and a `g f` chord added to the existing global key handler (through the `shouldIgnoreShortcut` editable-focus guard — no collision with `Cmd/Ctrl-K`, the `g s/c/l` chords, standalone `f`/`?`/`/`). Ship's Log was rewired off its old GLOBAL `writePref("logFilters", …)` / `useState(groupByPhase)` onto the per-voyage deck store keyed on the active `voyageId`, and now restores/saves the ships-log scroll position per voyage; single-voyage filtering behavior is byte-identical (no test regressed). A `useTrackDeckView(view)` hook called by each of the three view components records `lastView` per voyage so the switcher lands you back exactly where you left.
**Why**: Per-voyage keying (a `Record<voyageId, DeckUiState>`), not a global blob, IS the feature — it's the only shape that makes a switch lossless and bleed-free. The deck-state store is deliberately a SIBLING of `voyage.ts`, not a fork of it: `voyage.ts` owns the heavy per-voyage event ring + LRU eviction (P12) and the `selectVoyage` switch primitive; layering UI state on the SAME `voyageId` key keeps a single switch path and avoids duplicating event buffering. Reusing `readPref`/`writePref` (rather than a bespoke persistence path) inherits the established versioned-localStorage contract: a `DECK_STATE_VERSION` bump falls back to defaults instead of throwing on stale data, and the `localStorage`-undefined guard makes SSR safe for free. Returning defaults for an unknown voyage (without writing an entry) means a never-visited voyage reads cleanly and the persisted map stays small — only voyages you've actually touched are stored. The switcher reuses Command-Palette styling, the `ui`-store open-flag pattern, and the existing global key handler so it feels native and Esc/shortcut behavior stays consistent. Unlike `voyage.ts`'s LRU (which EVICTS event buffers for all but the active + 2 most-recent voyages to cap memory), deck UI state is tiny and is NOT evicted — it persists for every visited voyage so switching back is always lossless, even to a voyage whose event buffer was dropped.
**Don't suggest**: a single global deck-UI blob instead of per-voyage keying (that's exactly the bleed this removes), re-implementing event buffering or the LRU inside `deckState.ts` (call `voyage.ts`'s `selectVoyage` — it owns events + `visitedOrder`), a bespoke localStorage path instead of `readPref`/`writePref` (reuse the versioned helper — one persistence contract, SSR-safe), writing an entry into the map just to read defaults for an unknown voyage (`getDeckState` returns defaults without mutating), evicting deck UI state under the voyage-store LRU (UI state is tiny and must survive so switching back is lossless — only event buffers are LRU-capped), a keyboard shortcut that bypasses `shouldIgnoreShortcut` or collides with `Cmd/Ctrl-K` / the `g s/c/l` chord / `f`/`?`/`/`, keeping Ship's Log's old global `writePref("logFilters", …)` (it now keys on the active voyage), unguarded `window`/`localStorage` access (SSR-guarded via the helper).

## Decision: Bedside Browser — browser-in-the-loop verification behind a swappable backend (Phase 23)
**Date**: 2026-06-22
**What was decided**: Added the **Bedside Browser**, the Doctor's browser-in-the-loop verification — the GrandLine adaptation of PandaOS "test in a real browser to verify the fix". GrandLine's Doctor validated only via `pytest`; the Bedside Browser adds the second half — drive a headless browser against a running app, assert the page renders, and surface a screenshot in the Ship's Log: "tests pass AND the page renders". Real browser execution sits behind a **swappable `BrowserCheckBackend` ABC selected by a factory** (`app/browser/`), exactly mirroring `ExecutionBackend`/`DeploymentBackend`: `async run(spec: BrowserCheckSpec) -> BrowserCheckResult` + `async close()`, with `BrowserBackendError` for backend-internal failures (a check that merely fails its assertions returns `passed=False`, it does not raise). The **v1 default is `NullBrowserBackend`** — deterministic, browser-free, CI-safe (the analogue of `InProcessDeploymentBackend`): each assertion passes unless its `value` is empty (an empty selector/text is a malformed, failing assertion), and a placeholder screenshot ref `"null-backend://<name>.png"` is returned when `capture_screenshot`. `PlaywrightBrowserBackend` is the opt-in REAL backend that **lazily imports Playwright inside `run`** (never at module top level) and raises a clear `BrowserBackendError` with install guidance if Playwright is absent. `create_browser_backend(settings)` selects on the new `browser_backend: str = "null"` setting (env `GRANDLINE_BROWSER_BACKEND`); unknown -> `ValueError`. Schemas (`app/schemas/browser_check.py`): `BrowserAssertion` (`type: Literal["selector_present","text_present"]`, `value`), `BrowserCheckSpec` (`name`/`url`/`wait_for`/`assertions`/`capture_screenshot`), `BrowserCheckResult` (`passed`/`screenshots`/`console_errors`/`failed_assertions`/`duration_ms`), `BrowserCheckRead` (`from_attributes`). New `BrowserCheck` model (`browser_checks` table; `voyage_id` FK indexed, nullable `phase_number`, `url`, `passed`, nullable `screenshot_ref`, JSONB `console_errors`/`failed_assertions`, `created_at`); migration `b8d4f2a6c1e3` chains to head `a7c9e1f3b5d2`. `BedsideBrowserService(session, mushi)` mirrors Doctor commit/refresh/publish ordering: `run_browser_check(voyage, phase_number, spec, backend)` runs the spec via the INJECTED backend, persists a `BrowserCheck`, records a `BROWSER_CHECK_RUN` CrewAction (new `CrewActionType` member; `CrewRole.DOCTOR`) whose `details` carry `screenshot_ref` + `passed` so the Ship's Log surfaces the screenshot, commits atomically, then publishes the crew-action event best-effort. API (default-deny, owner-scoped via `get_authorized_voyage`): `POST /api/v1/voyages/{id}/phases/{phase_number}/browser-check` -> 201 `BrowserCheckRead` (backend pulled from `request.app.state.browser_backend`), `GET /api/v1/voyages/{id}/browser-checks` -> list. App lifespan constructs `app.state.browser_backend = create_browser_backend(settings)` and closes it on shutdown, next to the execution/deployment backends. Playwright is NOT added to `requirements.txt` (opt-in: `pip install playwright && python -m playwright install chromium`).
**Why**: The Doctor's existing "green tests" signal misses the failure PandaOS's demo catches — code that compiles and passes unit tests but renders a blank page. Adding a browser check closes that gap without diluting the crewed-pipeline story: it's the Doctor going to the bedside. Putting browser execution behind the SAME clean-ABC-behind-a-factory seam as `ExecutionBackend`/`DeploymentBackend` is non-negotiable — a real browser is heavy, flaky, and platform-specific, so it must be swappable and absent by default. The Null backend (not Playwright) is the CI default for the same reason `InProcessDeploymentBackend` is the deploy default: tests and app startup must never require a browser, a Playwright install, or `playwright install chromium` to be green. The lazy import inside `run` (rather than at module top) is what makes that guarantee hold even when the Playwright backend module is imported — importing the class never imports the library. Surfacing the result through a `BROWSER_CHECK_RUN` CrewAction carrying the `screenshot_ref` reuses the one durable Ship's Log write path (P8 locked taxonomy — the enum member is the sanctioned way, not an ad-hoc string) so the screenshot rides the same observability rails as every other crew action.
**Don't suggest**: importing Playwright at module top level (it must be lazy inside `run`, or app startup/tests break when it's absent), making Playwright the default backend (Null is the CI-safe default — Playwright is opt-in via `GRANDLINE_BROWSER_BACKEND`), adding `playwright` to `requirements.txt` (it's an optional dependency, documented as a manual opt-in install), raising an opaque `ImportError` when Playwright is missing (raise `BrowserBackendError` with install guidance), an ad-hoc `action_type` string for the Ship's Log entry instead of the `BROWSER_CHECK_RUN` enum member (P8 rejects ad-hoc strings), failing/raising on a check that merely fails its assertions (that's `passed=False`, not a `BrowserBackendError`), running the real browser in CI (the integration suite mocks the seam — Null backend in tests), building the backend inside the service instead of injecting it from `app.state` (the seam is the swap point, same as execution/deployment).

## Decision: Return Bottle — best-effort completion-time write-back closes the loop (Phase 22)
**Date**: 2026-06-22
**What was decided**: Added the **Return Bottle**, the completion-time outreach that closes the loop PandaOS's demo closes by "drafting a reply to the reporter". On a successful pipeline run — AFTER the `PIPELINE_COMPLETED` CrewAction is committed in `PipelineService.start` (~line 216) — a best-effort `ReturnBottleService(self._session, settings).report(voyage, ...)` call (a) posts a friendly themed voyage summary back as a comment on the originating GitHub issue when the voyage carries a Phase 21 `github_issue` `origin`, and (b) records a Log Book `summary` entry for `voyage.target_repo` so future voyages recall this voyage's outcome. `ReturnBottleService(session, settings)` + `ReturnBottleError(code, message)` exposes: `build_summary(voyage, *, deployment_url, duration_seconds, phase_count=None) -> str` (PURE, no I/O — title/status/phases/deploy-URL-if-any/duration); `async post_to_github_issue(origin, body) -> bool` (parses `origin["repo"]` as `owner/name`, POSTs `{base}/repos/{owner}/{name}/issues/{number}/comments` with `Authorization: Bearer <github_api_token>` + `Accept: application/vnd.github+json` + JSON `{"body": body}` via `httpx.AsyncClient` created inside the method; True on 2xx, False on non-2xx/empty-token/malformed-origin); and `async report(...) -> {"issue_commented": bool, "log_book_recorded": bool}` (gates each leg on `origin.type == "github_issue"` / `target_repo` and swallows + logs every exception). The completion hook re-fetches the voyage (`session.get(Voyage, id)`) so `origin`/`target_repo` are loaded, and is wrapped in a try/except that logs a warning and NEVER raises. New setting `github_api_base_url: str = "https://api.github.com"` (env `GRANDLINE_GITHUB_API_BASE_URL`) for testability; auth REUSES the existing `github_api_token`. Manual re-send API `POST /api/v1/voyages/{voyage_id}/return-bottle` (default-deny via `get_current_user`, owner-scoped via `get_authorized_voyage`): 404 missing/not-owned, 409 `VOYAGE_NOT_COMPLETED` if status != COMPLETED, else returns the result dict. No migration (no new columns). **This satisfies the Phase 19 Log Book deferral**: "auto write-back from completed voyages" — explicitly punted to "Phase 22 Return Bottle territory" — is now implemented as the `summary` write-back leg.
**Why**: GrandLine's pipeline ended at "Helmsman deploys" — the human who filed the issue never heard back. Reading the Phase 21 `origin` (the seam built precisely for this) lets the crew reply on the same channel the work arrived on. Making the whole thing best-effort AFTER the completion commit is non-negotiable: a flaky GitHub API or a malformed `origin` must never fail, roll back, or change the status of a voyage that already succeeded — the deploy is the source of truth, the bottle is a courtesy. The outbound host is FIXED to `github_api_base_url` and never derived from `origin`, so untrusted payload data can't redirect the bearer token at a host we don't control (mirrors the Phase 9 git-host-allowlist reasoning). Reusing `github_api_token` (not a new secret) keeps the credential surface flat. The Log Book write-back per repo is the natural place to honour Phase 19's deferral — a completed voyage is exactly the moment a durable, repo-scoped `summary` becomes available, and routing it through `LogBookService.record` reuses the one write path. The manual API exists so a fleet admiral can close the loop by hand when the automatic outreach failed.
**Don't suggest**: failing or rolling back a completed voyage when the Return Bottle fails (best-effort is the whole point — the deploy already succeeded), deriving the outbound GitHub host from `origin` (fixed `github_api_base_url` only — `origin` is untrusted), adding a new token setting (reuse `github_api_token`), logging the token, posting before the `PIPELINE_COMPLETED` commit (the commit is the durable success signal the bottle reports on), making the httpx client an instance attribute (create it inside the method, `async with`), a new Alembic migration (no new columns), recording the Log Book write as a different `kind` than `summary` (the taxonomy is locked; `summary` is the right bucket), re-implementing a separate Log Book write path instead of calling `LogBookService.record`.

## Decision: Message in a Bottle — HMAC-verified inbound webhook charts a course from a GitHub issue, recording origin metadata (Phase 21)
**Date**: 2026-06-22
**What was decided**: Added **Message in a Bottle**, an inbound external trigger that charts a course from a GitHub issue — the GrandLine adaptation of PandaOS's flagship "start work from an email / GitHub issue" demo. New nullable `origin` JSONB column on `Voyage` (migration `a7c9e1f3b5d2`, chained to the Phase 20 head `f6a1b2c3d4e5`): the **canonical record of how a voyage was triggered** (`{type, repo, issue_number, issue_url, issue_title, sender, received_at}`), NULL for a manually-charted voyage. New settings (env only): `github_webhook_secret` (`GRANDLINE_GITHUB_WEBHOOK_SECRET`), `trigger_default_user_email` (`GRANDLINE_TRIGGER_DEFAULT_USER_EMAIL`), `trigger_label` (`GRANDLINE_TRIGGER_LABEL`, default `"grandline"`). `app/schemas/trigger.py` models a minimal, `extra="ignore"` subset of the GitHub `issues` payload (action; issue number/title/body/html_url/labels; repository full_name/clone_url; sender login) plus `TriggerResult(status: "charted"|"ignored", voyage_id?, reason?)`. `TriggerService(session)` with `TriggerError(code, message)` exposes: a module-level `verify_github_signature(raw_body, signature_header, secret)` (HMAC-SHA256 over the raw bytes, **constant-time** `hmac.compare_digest` against the `sha256=` hex in `X-Hub-Signature-256`; `secret is None`/missing/malformed -> `False`); `should_trigger(payload)` (gate: `action in {opened, labeled}` AND `trigger_label` present on the issue); `resolve_trigger_user()` (look up `trigger_default_user_email` -> `TRIGGER_USER_UNCONFIGURED` if unset / `TRIGGER_USER_NOT_FOUND` if absent); and `ingest_github_issue(payload, user)` which charts a `CHARTED` voyage (title truncated to 255, description = body, target_repo = clone_url or full_name) reusing `voyages._default_dial_config` and setting the `origin` dict, committed atomically. API `POST /api/v1/triggers/github` reads the RAW body BEFORE JSON parsing, verifies the signature against `settings.github_webhook_secret` (401 `INVALID_SIGNATURE` on failure OR unconfigured secret), then: `should_trigger` False -> 200 `ignored`; `TRIGGER_USER_UNCONFIGURED` -> 422; `TRIGGER_USER_NOT_FOUND` -> 503; success -> 201 `charted` with `voyage_id`. The endpoint is the **single deliberate relaxation of default-deny**: it carries no Bearer token and is allowlisted by exact path in `PUBLIC_PATHS` (`/api/v1/triggers/github`), HMAC-verified at the route instead.
**Why**: The trigger must accept a payload from GitHub, which can't present a GrandLine Bearer token — so HMAC over the shared secret replaces it, keeping the rest of default-deny intact (one allowlisted path, signed). Rejecting when the secret is unset (rather than waving payloads through) means a misconfigured deployment fails closed, never open. Verifying over the **raw bytes** before parsing is mandatory: GitHub signs the exact body it sent, so a re-serialized Pydantic model would not match. The `origin` JSONB column (not a side table) is the smallest seam that carries provenance with the voyage it describes; Phase 22 "Return Bottle" reads it directly to reply back to the issue, so getting its shape right now is load-bearing. Reusing `_default_dial_config` guarantees a triggered voyage is byte-identical in configuration to a manual `POST /voyages` — one source of truth for "the default". Resolving the owning user from config (not the webhook) keeps the trigger free of any identity GitHub can't supply, while letting operators choose which account owns triggered voyages.
**Don't suggest**: accepting unverified payloads when the secret is unset (fail closed — 401), verifying the signature against a re-serialized model instead of the raw request bytes (the digests won't match), a non-constant-time signature compare (timing leak — `hmac.compare_digest` is required), Bearer-authing the webhook (GitHub can't present one — HMAC is the point), a separate triggers/origins table instead of the `Voyage.origin` column (the column is the seam Phase 22 consumes), a bespoke dial config for triggered voyages (reuse `_default_dial_config` — no divergence), deriving the owning user from `sender.login` (a GitHub login is not a GrandLine user — resolve from config), charting on every issue action/label (gated to `opened`/`labeled` + the configured label so the webhook stays quiet), widening `PUBLIC_PATHS` with a prefix rather than the single exact path (only `/api/v1/triggers/github` is relaxed).

## Decision: Standing Orders — reusable voyage presets that chart a configured voyage in one call (Phase 20)
**Date**: 2026-06-22
**What was decided**: Added **Standing Orders**, named per-user bundles of `{dial config + optional plan skeleton + injected context + default target repo}` that stamp a fully-configured voyage in one call — the GrandLine adaptation of PandaOS's "saved workflows / agent setups". New `StandingOrder` model (`standing_orders` table): `user_id` FK (owner, indexed, NOT NULL), `name` (`String(255)`), `description`/`injected_context` (`Text`, nullable), `target_repo` (`String(500)`, nullable), `dial_config`/`plan_skeleton` (JSONB, nullable), timestamps, and a unique constraint on `(user_id, name)` so a name is unambiguous per owner. `StandingOrderService(session)` with `StandingOrderError(code, message)` exposes owner-scoped CRUD (`create`/`get`/`list_for_user`/`update`/`delete`) plus `chart(order, *, task, title=None, target_repo=None) -> Voyage`. Charting **mirrors `voyages.create_voyage`** (creates a `CHARTED` voyage + seeds a `DialConfig` in one atomic commit) but with two preset behaviors: (1) the voyage's `DialConfig` is seeded from `order.dial_config`'s `{role_mapping, fallback_chain}` bundle when present, else from the SAME `_default_dial_config` `voyages.py` uses (imported/reused — no divergence between the two charting paths); (2) when `order.injected_context` is set it is **prepended** to the voyage `description` (`injected_context + "\n\n---\n\n" + task`) so the framing travels with the voyage rather than being silently dropped. `order.name`/`order.target_repo` are the title/repo defaults; per-chart `title`/`target_repo` overrides win. REST API at `/api/v1/standing-orders` (kebab, default-deny via `get_current_user`, owner-scoped): `GET`/`POST` (201) collection, `GET`/`PATCH`/`DELETE` (204) item, and `POST /{id}/chart` -> `VoyageRead` (201). `StandingOrderError("NOT_FOUND")` maps to 404. `dial_config` bundle shape is lightly validated at the schema boundary (`role_mapping` must be a dict; `fallback_chain` reuses the Dial System's `validate_fallback_chain`). Migration `a1b2c3d4e5f6` chains to the Phase 19 head `e5f6a1b2c3d4`.
**Why**: GrandLine's dial config is per-voyage — every `POST /voyages` seeds a fresh default config and re-picks repo/context from scratch. Recurring task shapes ("bugfix voyage", "dep-bump voyage") repeat that setup every time. A preset that stamps the whole bundle in one call removes that toil while producing an ordinary `Voyage` — the preset is a stamp, not a live link, so editing an order later never mutates voyages already charted from it. Reusing `voyages.py`'s `_default_dial_config` for the no-preset path guarantees a charted-from-order voyage with no `dial_config` is byte-identical to a plain `POST /voyages`, so there's one source of truth for "the default". Prepending `injected_context` to the `description` (rather than inventing a new column or dropping it) means the framing reaches the Captain through the existing planning surface — the description is already what `chart_course` plans from — with zero new plumbing. Owner-scoping at the query level (foreign id is indistinguishable from missing → `NOT_FOUND`/404, never 403) avoids leaking the existence of other users' presets.
**Don't suggest**: a live link from voyage back to its originating Standing Order (the preset is a stamp at chart time; mutating an order must not retroactively change charted voyages), a separate `default_dial_config` for the order path (reuse `voyages._default_dial_config` — one source of truth), a new column to carry `injected_context` into the voyage (the description is the existing planning surface; prepending is sufficient), materializing `plan_skeleton` into a `VoyagePlan` at chart time in this phase (it's stored as opaque JSONB; pre-seeded plans are a noted follow-up), sharing Standing Orders across users (they're per-user presets by design), returning 403 for a foreign id (leaks existence — `NOT_FOUND`/404 is deliberate), pre-checking `(user_id, name)` uniqueness in the schema (the DB unique constraint is authoritative; a pre-check races).

## Decision: Log Book — per-repo cross-voyage memory the Captain recalls at planning time (Phase 19)
**Date**: 2026-06-22
**What was decided**: Added the **Log Book**, a per-repo knowledge store that persists ACROSS voyages — the counterpart to Vivre Cards, which only checkpoint state WITHIN a voyage. New `LogBookEntry` model (`log_book_entries` table) keyed on `repo` (`String(500)`, indexed; matches `Voyage.target_repo`), with a nullable `voyage_id` FK (the voyage that produced the learning, if any), `author` (crew role string or `"user"`), `kind` (locked taxonomy: `convention`/`decision`/`layout`/`gotcha`/`summary`), `content` (`Text`), JSONB `details`, and `created_at`. Composite index `(repo, created_at)` powers most-recent-first recall. `LogBookService(session)` exposes `record(...)` (add+flush+commit+refresh, mirroring `CaptainService` commit ordering), `recall(repo, *, limit, kinds)`, and `render_context(repo, *, limit)` which returns a prompt-injectable markdown block headed `## Log Book — prior knowledge for <repo>` (or `""` when empty so callers no-op safely). **Captain integration**: `CaptainService.__init__` constructs a `LogBookService` from the same session (NOT in `reader()`); `chart_course` calls `render_context(voyage.target_repo)` BEFORE invoking the graph and, when non-empty, prepends it to the planning task (`recalled + "\n\n---\n\n" + task`). This is **best-effort** — wrapped in try/except, logs a warning on failure, and proceeds with the original task; no behavior change when `target_repo` is `None` or the Log Book is empty. **Write path is API-driven**: `GET /api/v1/log-book?repo=&limit=` and `POST /api/v1/log-book` (201), both default-deny via `get_current_user`. Migration `e5f6a1b2c3d4` chains to the current head `d4e5f6a1b2c3`.
**Why**: PandaOS's "local knowledge graph — never re-explain your stack" pitch maps cleanly onto GrandLine's voyage model as cross-voyage memory. Keying on `target_repo` (an existing column) means any voyage against the same repo shares one body of prior knowledge with zero new join machinery. Recall-at-planning is the highest-leverage injection point: the Captain's decomposition sets the shape of the whole voyage, so prior layout/conventions/gotchas there propagate to every downstream crew member for free. Making recall best-effort keeps a flaky read from ever blocking planning — the Log Book is an enhancement, not a dependency. Building the `LogBookService` in `__init__` (not `reader()`) keeps read-only Captain paths free of the recall machinery they don't use. API-driven writes ship a complete, testable feature now; auto write-back from completed voyages is a deliberate follow-up (Phase 22 "Return Bottle" territory) so we don't couple this phase to summary-generation quality.
**Don't suggest**: a global/shared knowledge graph across repos (the per-repo key is the whole point — different repos have different stacks), making Captain recall blocking/fatal (best-effort is non-negotiable), recalling inside `CaptainService.reader()` (read paths don't plan), storing learnings in Vivre Cards (those are voyage-scoped and ephemeral by design), an open `kind` free-text field (the locked taxonomy keeps recall renders predictable), auto-writing entries from every completed voyage in this phase (deferred — needs a quality gate), embedding/vector search for recall (most-recent-first + kind filter is sufficient at this scale; revisit if entry counts explode).

## Decision: claude_code provider folds the role prompt into the user turn and disables tools
**Date**: 2026-06-19
**What was decided**: The `claude_code` Dial System adapter (`app/dial_system/adapters/claude_code.py`) no longer passes each crew role's system prompt via `--append-system-prompt`. Instead `_build_prompt` folds the system instructions into the *user turn* (`"{system}\n\n=== INPUT ===\n{body}{_RESPONSE_CONTRACT}"`) and returns `system=None`, and `_command` always appends `--tools ""` to disable all CLI tools. A module-level `_RESPONSE_CONTRACT` reminder ("non-interactive completion endpoint, no tools/files, return only the requested output, no preamble/fences, put code inside the requested JSON field") is appended whenever a system prompt is present; pure single-user and multi-turn calls (no system message) pass through unchanged. The adapter's `--max-turns` default stays 1. Scope is adapter-only — crew prompts, the Dial router, guards, the pipeline graph, and the other providers (`anthropic`/`openai`/`ollama`) are untouched. Affected unit tests in `tests/test_dial_claude_code_adapter.py` were updated (`test_system_message_folded_into_user_turn`, `test_complete_builds_expected_command`).
**Why**: The Claude Code CLI is an agentic coding tool, not a text-completion API. ## Decision: Observation Deck backend prereqs — durable CrewAction log + WS transport + cookie auth bridge (Phase 16.0)
**Date**: 2026-05-07
**What was decided**: Phase 16.0 retrofits the Phase 15 backend with the four pieces the Observation Deck frontend needs. (1) **Durable CrewAction log**: every crew service (`captain`, `navigator`, `doctor`, `shipwright`, `helmsman`, `pipeline`) writes one or more `CrewAction` rows in the same `AsyncSession` as its existing main commit — failed inserts roll back the whole service operation, so the log is durable, not best-effort. The new `app/services/crew_action_helper.py` provides `record_action(session, voyage_id, crew_member, action_type, summary, details)` and `publish_crew_action_recorded(mushi, voyage_id, crew_action)`; the helper enforces the **`CrewActionType` enum** (P8 — backend rejects ad-hoc strings) and generates an `event_id` into `details["event_id"]` so the frontend can dedupe a `crew_action_recorded` WS event against the row (P3 correlation). (2) **WebSocket transport**: new `WS /api/v1/voyages/{id}/events` accepts `?token=<jwt>` for auth, opens an ephemeral Redis consumer group (mirror of the Phase 15.4 SSE forwarder), and forwards each event as `{"type": "event", "payload": {"msg_id": str, "event": <dump>}}` — a forward-compatible envelope so Phase 17 can add upstream `{"type": "intervention", ...}` messages without breaking Phase 16 clients. Close codes: **1008** for auth failure (P4: client refresh+reconnect), **1003** for voyage not found / not owned, **1000 + reason `"voyage-terminal"`** when the voyage flips to COMPLETED/FAILED/CANCELLED (P10: client transitions to `terminal-idle`, no retry). (3) **Cookie auth bridge**: `/auth/login`, `/auth/register`, and `/auth/refresh` now set `Set-Cookie: access_token=<jwt>; SameSite=Lax; HttpOnly=false; Max-Age=<exp>` in addition to returning JSON. New `POST /auth/logout` clears the cookie. HttpOnly is intentionally false because the WS handshake URL is constructed by JS (no header auth on `WebSocket`); the trade-off is documented and revisitable when Phase 17/18 tightens the threat model. (4) **Paginated list endpoints**: `GET /api/v1/voyages` (P7: `(updated_at, id) DESC` with opaque base64 cursor and optional `?status=active|terminal`) and `GET /api/v1/voyages/{id}/crew-actions` (P6: `(created_at, id) DESC` with the same cursor scheme). Cursor encoding lives in a shared `app/api/v1/_cursor.py` helper. Three new event types added to `app/den_den_mushi/events.py`: `PhaseBuildStartedEvent`, `PhaseBuildFailedEvent` (required by the P5 playback reducer) and `CrewActionRecordedEvent` (carries `crew_action.created_at` per P13 canonical timestamp).
**Why**: The Observation Deck UX requires data + transport guarantees the Phase 15 surface didn't yet provide. CrewAction durability fixes the "Redis publish fails after DB commit, log row vanishes from UI" gap (P9 frontend handles the reconciliation, but the row must actually exist). The WebSocket transport matches `conventions.md` line 116 (WS for live deck updates, SSE for token streaming) and gives Phase 17's bidirectional intervention a transport that's already in place. Cookie issuance is the smallest backend change that lets the existing Next.js middleware gate routes without pulling in a parallel session-cookie auth scheme. Cursor pagination on `(timestamp, id)` (not bare timestamp) is the only pagination shape that doesn't duplicate or skip rows when timestamps collide — a real edge case for high-throughput voyages. Locking the `CrewActionType` enum prevents string drift across crew services that would otherwise break the frontend Ship's Log grouping.
**Don't suggest**: writing CrewAction rows best-effort post-commit (defeats durability), forwarding raw `DenDenMushiEvent` over WS without the `{type, payload}` envelope (no upgrade path for Phase 17), HttpOnly cookies + same-origin proxy for WS auth (out of scope; revisit for prod), bare-timestamp pagination (P6/P7 lock cursor), localStorage tokens for the frontend (worse XSS surface than the deliberately-non-HttpOnly cookie that the middleware also reads), promoting WS to the only transport (SSE stays for Dial System token streaming), `event_type`-keyed dedupe (P3 locks `event_id`).

## Decision: PAUSED voyages resume via explicit `POST /resume` endpoint, not implicit `/start` status flip
**Date**: 2026-04-25
**What was decided**: Added `POST /voyages/{id}/resume` (issue #40 fix) that flips `voyage.status` from PAUSED (or FAILED) back to CHARTED via `PipelineService.resume(voyage)` and then spawns the pipeline task using the same `app.state.pipeline_tasks` registry plumbing as `/start` (factored into a private `_spawn_pipeline_task` helper to avoid duplication). `POST /start` now rejects PAUSED with a clear 409 `VOYAGE_PAUSED_USE_RESUME` error instead of silently no-oping (the previous behavior — the graph's per-stage `if status == PAUSED` check would route immediately to `pause_end`). Idempotency table for `/resume`: PAUSED/FAILED -> 202 (flip + spawn), CHARTED -> 202 (no flip, spawn), COMPLETED/CANCELLED/PLANNING/PDD/TDD/BUILDING/REVIEWING/DEPLOYING -> 409 `VOYAGE_NOT_RESUMABLE`, running task in registry -> 409 `PIPELINE_ALREADY_RUNNING`. Two new error codes registered in `_PIPELINE_ERROR_STATUS`: `VOYAGE_NOT_RESUMABLE` (409) and `VOYAGE_PAUSED_USE_RESUME` (409). The graph's per-stage PAUSED checks in `pipeline_graph.py` are unchanged; this fix lives entirely at the API + service layer because the graph never sees PAUSED on the resume path. `StartVoyageRequest` is reused for `/resume` (same shape as `/start`); `task` is required by validation but unused on resume since Captain is skip-already-satisfied — documented in the endpoint docstring.
**Why**: An explicit endpoint is more discoverable in the OpenAPI surface, semantically distinct from "begin a fresh run", and gives the frontend a clean affordance for the eventual resume button. The implicit-flip alternative would have made `/start` overloaded ("kick this voyage forward from wherever it is") which contradicts the existing 409 semantics for COMPLETED/CANCELLED. Idempotency on CHARTED/FAILED keeps `/resume` safe to retry. Locating the status flip in `PipelineService.resume(voyage)` (not the endpoint body) keeps the endpoint thin and gives integration tests a clean seam — the Phase 15.5 PAUSED-resume test now seeds `status=PAUSED` and calls `service.resume(voyage)` before `service.start(voyage, ...)`, replacing the prior CHARTED-with-comment workaround.
**Don't suggest**: implicit status flip in `/start`, adding a `force=true` body field, deriving the resume target stage from `phase_status` (skip-already-satisfied already does this), reading the previous status from a Voyage history table (no such table), changing the graph's per-stage PAUSED checks (those detect a pause that happened DURING a run — still useful), adding a new VoyageStatus enum value (e.g. RESUMING), making `/resume` accept a different schema than `/start` (one shape is simpler, even if `task` is unused).

## Decision: Pipeline REST + SSE API on top of PipelineService; background tasks in `app.state.pipeline_tasks`; SSE via ephemeral consumer groups
**Date**: 2026-04-24
**What was decided**: Added `app/api/v1/pipeline.py` with five endpoints: `POST /voyages/{id}/start` (202 Accepted, spawns `asyncio.create_task(service.start(...))` registered in `app.state.pipeline_tasks: dict[uuid.UUID, asyncio.Task]` and cleaned up via `task.add_done_callback`), `POST /pause` / `POST /cancel` (200, idempotent on terminal status; `/cancel` also cancels the in-flight task), `GET /status` (uses `PipelineService.reader(session)` — no dial router / execution backend constructed), and `GET /stream` (SSE, `text/event-stream`, one fresh ephemeral consumer group per connection named `sse-<uuid>`, replay-from-start at `id="0"`, ~1s block timeout with `request.is_disconnected()` check each loop, terminates on voyage terminal status or client disconnect, destroys the group in the `finally` block). Running-pipeline idempotency on `POST /start` is 409 `PIPELINE_ALREADY_RUNNING`; COMPLETED voyage also 409. `StartVoyageRequest` has `task: str (10–5000 chars)`, `deploy_tier: Literal["preview"]`, `max_parallel_shipwrights: int | None (ge=1 le=10)`. Shutdown in `app/main.py` lifespan cancels in-flight tasks and awaits up to 5s. No `last-event-id` / SSE resume in v1.
**Why**: Making `POST /start` 202 + background task keeps the HTTP layer responsive — the graph run takes minutes, not milliseconds, and clients observe it via SSE. The registry is process-local and single-worker by design; a multi-worker deployment would need to move it to Redis, but v1 runs single-worker and the simplicity is worth more than the horizontal-scale story. Ephemeral per-connection consumer groups sidestep cross-client ack coordination: each SSE consumer gets its own replay and the group dies with the connection (clean finally cleanup). Terminating on DB voyage status — rather than a dedicated "stream-end" event — means the SSE endpoint doesn't need to know about every terminal event type; any final state flip closes the stream. Running-pipeline 409 forces callers to explicitly cancel + restart rather than silently stomping on an in-flight run. The 5s shutdown window gives spawning `PipelineFailedEvent` one chance to reach Redis before the loop tears down.
**Don't suggest**: Persisting `pipeline_tasks` to Redis for multi-worker (out of scope for v1), named SSE events (`event: pipeline_stage_entered\ndata: ...`) — the envelope already carries `event_type` inline, adding a dedicated "pipeline finished" event to terminate SSE (DB status flip is sufficient), reusing a named consumer group across SSE connections (ack coordination headache), making `/start` synchronous (blocks connection for minutes), `last-event-id` support (revisit when stream volume > ~100 events per voyage)

## Decision: Master pipeline graph invokes services directly; parallel Shipwright via topological layers + semaphore; pause/resume via DB status
**Date**: 2026-04-23
**What was decided**: Added `app/crew/pipeline_graph.py` (master graph composing Captain → Navigator → Doctor(tests) → Shipwrights → Doctor(validate) → Helmsman) and `app/services/pipeline_service.py` (thin orchestrator: `start`, `pause`, `cancel`, `get_status`). Graph nodes instantiate crew services directly (`CaptainService`, `NavigatorService`, `DoctorService`, `ShipwrightService`, `HelmsmanService`) — they do not invoke each crew's compiled sub-graph. Parallel building uses `topological_layers()` to group phases by dependency layer, then runs each layer's phases concurrently under an `asyncio.Semaphore(max_parallel_shipwrights)`. Pause/resume is implemented via `voyage.status == PAUSED` in the DB, checked between every stage — **not** via LangGraph checkpointers. Resume is "skip-already-satisfied-stages aggressive": each node calls the next guard, and if it passes, the stage's output already exists → skip the LLM call. Five pipeline-level events added (`pipeline_started`, `pipeline_stage_entered`, `pipeline_stage_completed`, `pipeline_completed`, `pipeline_failed`); SSE streams tap the existing `DenDenMushi` bus — no new SSE endpoint. The pipeline owns the terminal `voyage.status` transitions (`COMPLETED` in `finalize_node`, `FAILED` in `fail_end`); crew services retain their transient writes (`BUILDING`, `DEPLOYING`, etc.) but the pipeline does not re-orchestrate them.
**Why**: Direct service invocation keeps the graph thin and composable — wrapping each service in a sub-graph would double the node count, obscure the end-to-end flow, and require synchronizing two state models. Topological layers + semaphore is the simplest correct scheduling: respects dependencies, bounds concurrency, and fails fast on any phase's failure. DB-backed pause/resume leverages the existing voyage status field and avoids pulling in `langgraph.checkpoint` (extra dependency, redis/postgres checkpoint storage, state serialization headaches). Skip-already-satisfied turns the guard module (Phase 15.2) into a cheap resume engine — no need for a separate "what's done?" query pathway. Tapping `DenDenMushi` for SSE reuses the stream-key convention already shipped in Phases 10–14.
**Don't suggest**: LangGraph checkpointers for pause state, sub-graphs per crew (e.g. calling `captain_graph.ainvoke` from a planning node), per-stage `asyncio.gather` without a semaphore (would fan out unbounded), adding a separate "pipeline event stream" distinct from the voyage stream, moving terminal status writes into crew services, making the pipeline aware of `phase_status` transitions at the service level (Shipwright owns those).

**Why**: The GET endpoint is a simple DB read. Requiring a `DialSystemRouter` dependency means that if the voyage's DialConfig is deleted, the plan becomes unreadable even though it's already persisted. Decoupling read from write dependencies keeps the read path robust.
**Don't suggest**: Sharing the full `get_captain_service` dependency for read endpoints, creating a separate PlanReadService (over-abstraction for one method)

## Decision: Best-effort event publishing after DB commit
**Date**: 2026-04-14
**What was decided**: `chart_course` commits plan + VivreCard to PostgreSQL first, then publishes the `VoyagePlanCreatedEvent` to Den Den Mushi in a try/except. If Redis is down, the event is logged as a warning and the request succeeds.
**Why**: The plan is the source of truth, not the event. If publish fails after a successful commit, the caller gets a successful response and can retry the event later. Failing the request after the plan is already committed leaves the caller with a 500 for a successful write and no safe retry path (the voyage status has moved out of CHARTED).
**Don't suggest**: Publishing before commit (data loss risk), failing the request on publish failure, transactional outbox (premature for current scale)

## Decision: Shipwright invocation is phase-scoped
**Date**: 2026-04-17
**What was decided**: The Shipwright Agent's build API is phase-scoped (`POST /voyages/{id}/phases/{phase_number}/build`), not voyage-scoped. One invocation builds exactly one phase. The future voyage pipeline (Phase 15) fans out one invocation per phase to enable parallelism.
**Why**: Per-phase invocations are the parallelism primitive. A voyage-level endpoint would force serial phase builds, or require the Shipwright itself to manage internal parallelism — premature complexity. Scoping per-phase also keeps the LLM context small (one Poneglyph + its tests) and enables independent retries.
**Don't suggest**: Voyage-scoped build endpoint that loops over phases internally, hidden intra-Shipwright concurrency

## Decision: Service-owned iteration loop, graph stays side-effect-free
**Date**: 2026-04-17
**What was decided**: The Shipwright's generate→test→refine iteration loop is implemented in the **service layer**, not inside the compiled LangGraph graph. The service runs single-iteration graph invocations in a Python loop, writing a `VivreCard` between iterations for "no work lost" guarantees.
**Why**: LangGraph graphs should remain pure — nodes call LLMs and sandboxes but don't own DB state. Per-iteration checkpointing is a DB write; keeping it in the service preserves graph purity and makes the loop trivially testable with mocked graph invocations. The alternative (LangGraph's built-in checkpointer) adds infrastructure without solving the observability problem (we want one VivreCard row per iteration, queryable by the Observation Deck).
**Don't suggest**: Putting `session.commit()` inside graph nodes, relying on LangGraph's internal checkpointer for product-level state, one giant `.ainvoke()` that runs the full loop opaquely

## Decision: Shipwright voyage-level status gate (v1 scope-cut)
**Date**: 2026-04-17
**What was decided**: v1 of the Shipwright enforces a single in-flight invocation per voyage via the `voyage.status == CHARTED` gate (transitions to `BUILDING` during the call). True per-phase parallelism is deferred until a `phase_status` map is added to the voyage model.
**Why**: Shipping a correct sequential path first. Concurrent invocations on the same voyage would race the `voyage.status` transition and the `delete-before-insert` step for `BuildArtifact`. A `phase_status` refactor is the right long-term fix but premature for the first Shipwright cut. Phase 15's voyage pipeline will sequence phase builds; user-level fan-out across phases waits for the refactor.
**Don't suggest**: Removing the 409 gate, introducing a voyage-level lock in Redis (heavier than needed), bolting on a phase_status column without a migration plan
**Superseded by**: 2026-04-19 — Shipwright per-phase status gate (Phase 15.1 refactor)

## Decision: Shipwright per-phase status gate (Phase 15.1 refactor)
**Date**: 2026-04-19
**What was decided**: Replaced `voyage.status` gate with a `Voyage.phase_status` JSONB map keyed by `str(phase_number)` with values `PENDING | BUILDING | BUILT | FAILED` (module-level string constants in `shipwright_service.py`, no SQLAlchemy enum). `ShipwrightService.build_code` gates on `phase_status.get(key, "PENDING") in {"PENDING", "FAILED"}` and raises `ShipwrightError("PHASE_NOT_BUILDABLE")` → HTTP 409 when the phase is already `BUILDING` or `BUILT`. `voyage.status` is no longer touched by the service. `BuildArtifact` delete-before-insert remains scoped to `(voyage_id, phase_number)`.
**Why**: Phase 15's voyage pipeline wants to build independent phases in parallel (topological layers bounded by `asyncio.Semaphore`). The voyage-level gate made concurrent phase builds impossible — any second invocation 409'd, even for a different phase. Keeping `voyage.status` untouched lets the master pipeline own the outer `CHARTED → BUILDING → COMPLETED` transitions without racing the Shipwright. JSONB over a new table avoids a join on every gate check; dict-copy-before-assign keeps SQLAlchemy's JSONB dirty-tracking happy without `flag_modified`. Per-phase re-buildability (FAILED → buildable) is a pipeline-retry requirement.
**Don't suggest**: Reinstating the `voyage.status` gate, using a SQLAlchemy Enum column (JSONB values are more flexible and cheaper to migrate), introducing `flag_modified` everywhere instead of fresh-dict-assign, adding per-phase row locks (the status map is a single row update)

## Decision: Pipeline transition guards as pure predicates
**Date**: 2026-04-20
**What was decided**: Added `app/services/pipeline_guards.py` with six `require_can_enter_*` helpers (`planning`, `pdd`, `tdd`, `building`, `reviewing`, `deploying`) and a single `PipelineError(code, message)` exception distinguished by `.code`. Guards take DB-loaded objects (voyage, plan, poneglyphs, health_checks, build_artifacts, validation_run) and raise on violation — no DB queries, no LLM calls, no event publishing, no state mutation. Error code taxonomy is 1:1 with guards: `VOYAGE_NOT_PLANNABLE`, `PLAN_MISSING`, `PONEGLYPHS_INCOMPLETE`, `HEALTH_CHECKS_INCOMPLETE`, `BUILD_INCOMPLETE`, `VALIDATION_NOT_PASSED`. "Can enter reviewing" checks both `BuildArtifact` presence AND `voyage.phase_status[str(phase)] == "BUILT"` for every planned phase — the first consumer of the Phase 15.1 `phase_status` gate.
**Why**: The master pipeline has six stage transitions, each with different pre-conditions. Putting the checks inline in the graph nodes (Phase 15.3) would scatter invariants across six files and tangle scheduling with validation. Centralizing them as pure predicates means: one place to reason about "what does a voyage need to enter stage X," trivially unit-testable (no DB fixtures — 33 tests, 0.03s), and reusable as the engine for skip-already-satisfied-stages on resume. When a voyage resumes, the pipeline calls the *next* guard; if it passes, the stage's output already exists, so skip the stage + its LLM call entirely. That's token-cost savings on re-run after a fix.
**Don't suggest**: Merging the guard module into `pipeline_service.py` (the separation is the point), one-exception-per-guard (`PlanMissingError`, `PoneglyphsIncompleteError` — unnecessary class sprawl, use `.code`), guards performing DB lookups (couples them to sessions and makes unit tests require mocked sessions), adding guards for status transitions the pipeline doesn't use (e.g. `require_can_enter_completed` — `finalize_node` owns that)

## Decision: Configurable Shipwright concurrency via DialConfig (not env/global)
**Date**: 2026-04-19
**What was decided**: Added `ShipwrightRoleConfig.max_concurrency: int | None` (Pydantic `ge=1 le=10`) to `DialConfig.role_mapping.shipwright`. `resolve_shipwright_max_concurrency()` reads the value at pipeline-start time and falls back to `1` on any missing key, non-dict shape, validation failure, or `None`. No migration — piggybacks on the existing `role_mapping` JSONB.
**Why**: Different users have different provider plans — a free-tier Anthropic key can't sustain 5 concurrent Shipwrights, a Tier-4 key easily can. Hard-coding a global max would either starve high-tier users or overload low-tier ones. Per-voyage scoping (via DialConfig) means the knob sits next to the other provider choices the user already tunes. The `1..10` range is a safety rail — parallelism beyond 10 typically hits rate limits anyway and burns tokens on retries. Fail-safe-to-1 means a malformed config never triggers a fan-out storm.
**Don't suggest**: Global env var, per-request query param, removing the upper bound, raising on invalid config (silent fallback preserves "voyages always progress")

## Decision: Vitest deferred; Shipwright v1 is pytest-only
**Date**: 2026-04-17
**What was decided**: If a phase's `HealthCheck.framework == "vitest"`, `ShipwrightService.build_code` returns `ShipwrightError("VITEST_NOT_SUPPORTED")` → 422. pytest-only for v1. Vitest support is a follow-up feature.
**Why**: Running Node/Vitest inside the sandbox is a separate integration (different runtime, different pytest-vs-vitest output parsing, different file layout). Scoping v1 to pytest keeps the first Shipwright cut focused. The error code is explicit so the voyage pipeline can surface it cleanly.
**Don't suggest**: Silent fallback to pytest for Vitest tests, adding Vitest runner without a dedicated PDD cycle

## Decision: Shipwright max_iterations hardcoded to 3
**Date**: 2026-04-17
**What was decided**: `SHIPWRIGHT_MAX_ITERATIONS = 3` is a module-level constant, not an env/config value. The loop terminates on green tests or after 3 attempts (generate + run, 3x).
**Why**: Config surface area has a cost. 3 matches typical Claude/GPT-4 "fix your own output" attention span and keeps worst-case latency bounded. If Phase 15 integration tests show 3 is too low, bump the constant — no schema change, no API change. Adding an env var now signals "this is a knob we tune" when it's actually a best-effort convergence limit.
**Don't suggest**: Exposing `max_iterations` via API, reading from `.env` at startup, per-voyage overrides
